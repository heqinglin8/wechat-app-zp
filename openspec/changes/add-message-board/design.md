## 背景

当前小程序在 `pages/jobDetail/jobDetail`、`pages/seekerDetail/seekerDetail` 等详情页中直接使用页面级 Bmob 查询。留言板数据库继续采用 Bmob。留言板应独立于这些详情页，并作为每个详情页末尾的功能区挂载，而不是写成职位专用或求职信息专用的内嵌逻辑。

同一个留言板模块必须同时支持当前职位详情页和求职详情页，并为未来其他详情页接入保留扩展能力。本次变更中的运营控制能力，例如加精、置顶、隐藏、敏感词、用户禁言，不需要建设管理后台；这些配置和状态可以直接在数据库中维护。

## 目标 / 非目标

**目标：**

- 提供一个可复用的留言板模块，通过 `targetType + targetId` 挂载到业务详情页。
- 通过 `targetType=job` 支持职位详情留言，通过 `targetType=job_seek` 支持求职详情留言。
- 保持详情页接入足够轻量：详情页只传入目标身份和当前详情是否允许留言。
- 在展示留言板或接受留言操作前，同时校验全局开关和详情级开关。
- 支持文字、emoji/微信风格表情，以及每条留言最多一张可压缩、可预览的图片。
- 支持一级回复，并具备默认折叠展示行为。
- 支持隐藏、加精、置顶、敏感词过滤、全站禁言，以及绑定留言的物理删除。

**非目标：**

- 不建设后台管理或审核后台 UI。
- 用户收到回复时不发送通知。
- 详情页不展示留言数量。
- 不支持超过一级的嵌套回复。
- 职位或求职详情被删除后，不保留其绑定留言。

## 决策

### 使用 `targetType + targetId` 作为挂载模型

留言记录通过以下字段保存其所属业务对象：

- `targetType`：`job`、`job_seek`，以及未来其他模块标识。
- `targetId`：绑定业务记录的 object id。

这样可以避免为每个详情模块创建独立留言表或重复查询逻辑。职位留言和求职留言都变成同一留言模型上的过滤查询：

- 职位留言：`targetType == "job" && targetId == jobId`
- 求职留言：`targetType == "job_seek" && targetId == jobSeekId`

备选方案是分别建立 `JobMessage`、`JobSeekMessage` 等独立表。这样当前查询会更直观，但发布、回复、隐藏、敏感词、分页等行为会重复实现，未来新增模块的成本也会更高。

### 数据库继续采用 Bmob

留言板相关数据，包括留言、回复、全局开关、敏感词、用户禁言和留言状态，均存储在 Bmob 中，并沿用现有小程序的 Bmob SDK 查询和保存方式。

备选方案是引入新的数据库或服务端存储。当前项目已有 Bmob 使用基础，引入新存储会增加接入、权限和数据一致性成本，因此本阶段不采用。

### 将留言板保持为可复用页面组件/模块

留言板应暴露一个尽量小的接入面：

- 必填：`targetType`
- 必填：`targetId`
- 必填：`detailMessageEnabled`
- 可选：当前详情发布者/所有者信息，供未来需要时扩展

宿主详情页只负责决定是否挂载留言板，并传入目标身份。留言板模块自身负责加载、分页、发布、回复、折叠、图片选择和渲染。

在详情页中，留言板应作为普通内容流的最后一个内容区挂载，位置在详情正文内容之后、悬浮操作区域 `det-nav` 之前或上方。`det-nav` 继续保持原有悬浮/固定操作区行为，留言板不得改变 `det-nav` 的结构、交互和悬浮效果；页面需要为底部悬浮区域预留安全间距，避免留言板内容被遮挡。

```text
┌────────────────────┐        ┌────────────────────┐
│ pages/jobDetail     │        │ pages/seekerDetail  │
│ targetType=job      │        │ targetType=job_seek │
└─────────┬──────────┘        └─────────┬──────────┘
          │                             │
          └──────────────┬──────────────┘
                         ▼
              ┌────────────────────┐
              │ message-board       │
              │ component/module    │
              └─────────┬──────────┘
                        ▼
              ┌────────────────────┐
              │ Bmob message data   │
              └────────────────────┘
```

备选方案是把留言列表和发布表单直接复制到每个详情页中。这样初期会更快，但会破坏留言板模块独立性，也不利于未来扩展到更多详情页。

### 使用分层开关校验

留言板最终是否可用由以下表达式决定：

```text
globalMessageBoardEnabled && detailMessageEnabled
```

全局开关关闭时，所有留言板都不可用。详情级开关只控制当前绑定详情记录。如果留言板不可用，模块不应展示发布入口；任何发布路径也必须再次校验同一条件。

### 小程序端完全不展示隐藏留言

隐藏留言应从所有小程序端查询结果中排除，不区分用户角色，包括留言作者、管理员和详情发布者。数据库操作人员仍然可以直接在数据库中查看和恢复这些留言。

命中敏感词时，发布动作仍然成功，但创建出的留言默认隐藏，并向发布者展示 toast 提示。这样既保证发布流程结果明确，又能阻止内容公开展示。

备选方案是命中敏感词时直接禁止发布。当前选择符合“发布成功但默认隐藏”的产品要求，并允许后续人工恢复。

### 只支持一级回复

回复记录保存主留言 id，不把“回复某条回复”作为新的嵌套层级。展示模型如下：

```text
留言
  ├─ 回复
  ├─ 回复
  └─ 回复
```

回复列表默认折叠。主留言发布者相关线程和当前用户自己的相关留言保持展开。主留言先按置顶优先排序，再按创建时间倒序排序。回复不支持置顶，并按创建时间倒序排序。

### 区分加精和置顶语义

加精是留言上的视觉标识。置顶会影响排序，并使该留言排在非置顶留言之前。一条留言可以只加精、只置顶、同时加精并置顶，或者两者都没有。

### 使用微信选择图片能力并避免重复压缩

发布留言选择图片时优先使用微信小程序自带的选择图片组件/能力。如果微信选择图片能力已经提供并完成压缩，则不再额外压缩，避免重复压缩影响画质和性能；如果选择结果仍未满足限制，则再使用补充压缩或直接拒绝。无论压缩来源如何，最终提交前都必须校验图片分辨率不超过 1080x960、大小不超过 1MB。

### 本阶段优先使用数据库维护运营控制

数据模型应包含支持以下能力的字段或集合：

- 全局留言板配置
- 全局敏感词配置
- 用户级全站留言禁言
- 留言隐藏、加精、置顶、删除等状态字段

本次变更不包含管理 UI。运营人员可以直接在数据库中更新这些记录。

### 绑定详情删除时使用物理删除

当用户尝试删除 `JobInfo` 或 `JobSeeker` 记录时，删除流程必须先弹窗提醒：“删除该记录会同时删除他的留言信息，确认删除？”。只有用户确认后，才继续删除详情记录，并物理删除所有匹配 `targetType + targetId` 的 `MessageBoardMessage` 记录，包括主留言和回复。用户取消时，不删除详情记录，也不删除任何留言。

如果删除动作存在多个入口，每个入口都必须调用同一个删除辅助方法或服务路径，避免产生孤儿留言。

## 风险 / 取舍

- 物理删除会永久移除审核/审计历史 → 这符合当前需求，但删除路径必须明确、必须先确认，并验证取消删除时没有任何数据被删除。
- 仅通过数据库操作运营配置容易上线，但对非技术运营人员不够友好 → 字段名和状态值应尽量简单，并在实现说明中记录。
- 只在客户端做敏感词过滤可能被绕过 → 过滤应在共享发布路径中执行，并发生在持久化前，而不是只放在 UI 层。
- 微信选择图片能力或补充压缩后仍可能超过 1MB → 最终提交前仍需校验，超限时用 toast 拒绝发布。
- 现有详情页存在悬浮操作区域 `det-nav` → 留言板应作为最后一个内容区挂载在 `det-nav` 上方，并预留安全间距，避免影响 `det-nav` 悬浮效果或被其遮挡。
- 未来模块可能需要不同可见性规则 → 保持 `targetType` 通用，但在没有真实新模块前不要过度泛化当前权限模型。
