## Context

当前 `pages/pubilshJobSeek/pubilshJobSeek` 已有学历 picker 和薪资区间输入，但缺少工种选择，导致 `JobSeeker.payType` 在推荐求职链路中依赖历史数据或默认值。与此同时，岗位/求职相关页面的薪资格式化函数分散在多个页面脚本内，存在“临时工按小时”“无单位”等不一致展示。

本次变更是一次跨页面口径统一：
- 录入层：发布求职时显式选择工种并写入 `payType`。
- 展示层：所有临时工展示位统一按 `元/天`，其余统一按 `元/月`。
- 规格层：将历史“按小时语义”统一为“按天语义”。

## Goals / Non-Goals

**Goals:**
- 在推荐求职发布页新增“工种”单选交互，并持久化 `payType`。
- 在发布页薪资行展示与工种联动的单位提示（`/月`、`/天`）。
- 统一岗位/求职列表与详情中的薪资单位语义，避免页面口径冲突。
- 将规范文档中的临时工薪资语义统一为“按天”。

**Non-Goals:**
- 不改动 Bmob 表结构（仅使用既有 `payType`、`detPayMin`、`detPayMax` 字段）。
- 不调整“临时工/高薪资”筛选逻辑和查询条件。
- 不引入新的后端接口或第三方依赖。

## Decisions

### Decision 1: 发布页工种复用学历 picker 交互
- **Choice**: 在 `pubilshJobSeek` 中新增 `payTypeOptions + payTypeIndex + onPayTypeChange`，交互方式与学历字段一致。
- **Why**: 页面已有成熟样式与交互模式，改动最小且学习成本低。
- **Alternative considered**: 使用自定义弹层选择器；被拒绝，原因是实现复杂度更高且无必要。

### Decision 2: 定义统一薪资单位映射规则
- **Choice**: 以 `payType` 为唯一单位映射来源：`1 -> 元/天`，其他值（含 `0` 与缺省）`-> 元/月`。
- **Why**: 规则可在所有页面复用，并覆盖历史缺省数据，减少展示分歧。
- **Alternative considered**: 保留“临时工按小时”；被拒绝，原因是与当前业务确认口径冲突。

### Decision 3: 分页面收敛薪资格式化函数
- **Choice**: 逐页更新现有 `salaryText/formatSalaryText/formatTopSalary`，在不重构目录的前提下统一单位输出。
- **Why**: 这些函数分散且耦合页面字段，局部改造风险低于一次性抽公用模块。
- **Alternative considered**: 新建全局薪资格式化 util 并全量迁移；被拒绝，原因是本次范围内收益不足，且迁移回归面过大。

### Decision 4: 详情页与卡片都按“语义 + 区间”展示
- **Choice**: 保持现有薪资数值显示形式（区间或单值），只统一单位后缀语义。
- **Why**: 可降低 UI 变更幅度，聚焦口径一致性，不引入额外排版风险。
- **Alternative considered**: 同步改为固定文案模板（如“X-Y 元/月”）；被拒绝，原因是会扩大改动并影响多个页面样式。

## Risks / Trade-offs

- **[风险] 多页面存在重复格式化逻辑，可能漏改某处单位** → **缓解**：通过关键字检索 `salaryText`、`元/小时`、`cardSalary`、`payTypeText` 做清单式修改与复核。
- **[风险] 历史数据缺失 `payType` 导致展示异常** → **缓解**：缺省值按“其他”处理并回落到 `元/月`。
- **[权衡] 未抽取公共 util 会保留一定重复代码** → **收益**：避免本次引入大范围重构风险，确保改动可控、可快速回归。

## Migration Plan

1. 更新发布页（`wxml/js/wxss`）新增工种选择与薪资单位后缀展示。
2. 更新 `applyJobSeekerFields` 写入 `payType`，保证新发布数据具备完整语义。
3. 逐页更新岗位/求职列表及详情页薪资格式化函数，统一单位规则。
4. 运行手工场景回归：`payType=1`、`payType=0`、`payType` 缺省三类样本。
5. 若发现展示回归，按页面回滚对应脚本文件，不影响数据库结构与已有查询条件。
