## Context（背景）

本项目是一个微信原生小程序，使用 ES6 和 CommonJS 模块，没有根目录 `package.json` 或前端构建流水线。现有城市相关逻辑集中在 `utils/city.js`：负责归一化微信 `picker mode="region"` 返回值、保存当前城市、向 Bmob 记录写入 `provinceName`/`cityName`/`districtName` 及其编码，并限制只能选择当前已开放业务城市。

本次变更要补充的是更底层的标准地区编码能力：给定 `440106` 这类区/县级行政区划代码，从小程序本地数据中查询完整的省、市、区/县编码和名称。该查询能力应离线可用，不依赖 Bmob、网络请求或微信地区选择组件。

## Goals / Non-Goals（目标 / 非目标）

**目标：**

- 复用项目内 `assets/pca-code.json` 作为小程序本地可用的全国省、市、区/县三级行政区划编码数据快照；该文件的数据来源采用国家统计局《统计用区划代码和城乡划分代码》。
- 提供 `findByDistrictCode(districtCode)` 工具方法，成功查询时返回：
  - `provinceCode`
  - `provinceName`
  - `cityCode`
  - `cityName`
  - `districtCode`
  - `districtName`
- 对格式错误或本地数据中不存在的区码返回 `null`，不回退到默认城市。
- 新查询能力与 `utils/city.js` 中已有的开放城市限制保持独立。
- 采用当前微信小程序运行环境可直接使用的代码和模块写法。
- 在查询工具或相邻元信息中记录本地文件路径、来源名称、来源入口和快照年份。

**非目标：**

- 不修改城市选择 UI，也不调整当前已开放业务城市列表。
- 不新增 Bmob 字段，不编写迁移脚本，也不做运行时历史数据补齐。
- 不增加基于网络的地理编码或行政区划动态更新能力。
- 不处理地址转编码、GPS 转编码等能力；本次只覆盖“编码查地区”。

## Decisions（设计决策）

1. **地区编码查询模块与当前城市业务逻辑分离**

   复用现有本地数据文件 `assets/pca-code.json`，新增独立的工具模块，例如 `utils/region.js`。`utils/city.js` 继续负责当前城市缓存、展示和开放城市校验。

   备选方案一是将数据和查询能力直接加入 `utils/city.js`。不采用该方案的原因是：`utils/city.js` 已经承载当前城市存储、展示和开放城市业务规则。将全国标准地区查询单独拆出，可以避免把“全国标准地区”与“当前业务已开放地区”混在一起。

   备选方案二是在 `utils/` 下再生成一份 `region-data.js`。不采用该方案的原因是项目已经存在 `assets/pca-code.json`，重复数据会增加维护成本和小程序包体积。

2. **使用紧凑的层级数据快照**

   `assets/pca-code.json` 已按省、市、区/县层级存储数据，结构为数组 + `children`。省级 `code` 通常为 2 位，例如 `44`；市级 `code` 通常为 4 位，例如 `4401`；区/县级 `code` 为 6 位，例如 `440106`。查询工具必须在返回结果中把省级、市级编码统一补齐为 6 位行政区划代码，例如 `44 -> 440000`、`4401 -> 440100`。

   当前数据文件的逻辑结构示例：

   ```js
   [
     {
       code: '44',
       name: '广东省',
       children: [
         {
           code: '4401',
           name: '广州市',
           children: [
             { code: '440106', name: '天河区' }
           ]
         }
       ]
     }
   ];
   ```

   工具 API 必须隐藏内部数据结构，调用方只感知标准返回对象。

3. **构建懒加载区码索引**

   `findByDistrictCode` 首次调用时构建模块级 `districtCode -> region` 索引，后续查询复用该索引。这样可以避免每次查询都遍历全国数据，同时保持模块初始化逻辑简单。

   备选方案是直接导出按区码索引的扁平对象。该方案查询最快，但会在数据文件中大量重复省市名称和编码，增加包体积，因此不作为首选。

4. **归一化入参，但不猜测缺失数据**

   查询工具应将入参转为去除首尾空白的字符串，并要求它必须是 6 位数字。未知、为空、格式错误或不完整的编码都返回 `null`。工具不能只根据编码前缀推断名称，也不能回退到 `广东省 / 广州市 / 天河区`。

   类似 `440106 -> 440000 / 440100` 的编码补全只能基于 `assets/pca-code.json` 中实际存在的层级关系完成；名称和特殊层级结构必须来自本地标准数据快照。

5. **保留标准数据源中的特殊行政层级**

   直辖市、自治州、盟、省直辖县级行政区划等特殊结构，也应返回包含省级、市级、区/县级信息的六字段对象。`cityCode` 和 `cityName` 应遵循所选标准数据源中的层级，不自定义简化规则。

6. **记录数据来源和快照年份**

   本地数据文件明确采用 `assets/pca-code.json`，其数据来源为国家统计局《统计用区划代码和城乡划分代码》。查询工具或相邻元信息应记录本地文件路径、来源名称、来源入口和快照年份，方便后续行政区划更新时追踪和替换。

   推荐元信息结构：

   ```js
   var metadata = {
     localFile: 'assets/pca-code.json',
     sourceName: '国家统计局 统计用区划代码和城乡划分代码',
     sourceUrl: 'https://www.stats.gov.cn/sj/tjbz/tjyqhdmhcxhfdm/',
     snapshotYear: 'YYYY',
     level: 'province-city-district'
   };
   ```

   `snapshotYear` 必须填写实际采用的数据年份，例如实现时下载并整理的是 2024 年发布的数据，则填写 `'2024'`。

## Risks / Trade-offs（风险 / 权衡）

- **[风险] 全国本地数据会增加小程序包体积** → **应对：** 复用已有 `assets/pca-code.json`，不再复制一份数据到 `utils/`，不新增第三方依赖，并在实现时检查数据大小。
- **[风险] 行政区划会随时间变化** → **应对：** 明确记录国家统计局数据来源和快照年份，并保持数据模块可替换，方便后续更新。
- **[风险] 直辖市、省直辖县级行政区划等特殊情况处理错误** → **应对：** 保留标准数据源层级，并选取代表性特殊结构做验证。
- **[风险] 调用方修改返回对象后污染缓存数据** → **应对：** 返回扁平对象副本，或用其他方式确保调用方修改不会影响索引缓存。

## Migration Plan（迁移计划）

1. 复用 `assets/pca-code.json`，新增地区编码查询工具模块。
2. 针对代表性区码查询、无效编码和未知编码行为补充验证。
3. 只有在现有调用方明确需要区码反查时，才接入新工具。
4. 回滚时只需移除新增工具模块以及可选调用点；`assets/pca-code.json` 若已被其他功能使用则保留，不涉及后端回滚。
